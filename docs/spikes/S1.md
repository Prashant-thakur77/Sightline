# S1: Buyer dispute by API for an Orders v2 capture

## Question

Can Sightline open a buyer dispute through `POST /v1/customer/disputes` (multipart `input`, `PayPal-Auth-Assertion`
for the sandbox buyer) on a transaction captured through Orders v2? Where does `buyer_transaction_id` come from?
Live docs call create, change-reason and validate-eligibility limited release: they need the `disputes/create` and
`disputes/update-buyer` scopes (added by a PayPal account manager) and buyer consent through Log in with PayPal.

## What we ran

`packages/db/node_modules/.bin/tsx packages/paypal/spikes/run.ts s1-dispute` (uses the captured order from the
last `s2-vault` run; `--wait=SECONDS` controls how long to poll for a merchant-side dispute).

1. Transaction Search as the merchant for the capture id; as the buyer with the auth assertion (undocumented).
2. `POST /v1/customer/disputes/validate-eligibility` with three guessed body shapes (schema unpublished).
3. Buyer create with every candidate id (eligibility answer, buyer search, the capture id itself); a `payer_id`
   assertion as a last try when `PAYPAL_SANDBOX_BUYER_PAYER_ID` is set. Exact errors are kept.
4. Fallback: `POST /v2/customer-support/process-chargeback` on the capture (sandbox simulation), then polled
   `GET /v1/customer/disputes?disputed_transaction_id=` for a merchant-side dispute.
5. Printed the manual Resolution Center path (not automated): sign in at https://www.sandbox.paypal.com/signin as
   the sandbox buyer, open the payment from https://www.sandbox.paypal.com/myaccount/activity, or go to
   https://www.sandbox.paypal.com/resolutioncenter and report a problem.

## Decision

Proposed: neither buyer create nor chargeback simulation produced a dispute. Use (b) the sandbox Resolution Center for the buyer step, or (c) seller message plus refund, per the fallback ladder.
<!-- decision:end -->

## Fallback

(a) API with the id from Transaction Search; (b) automate the sandbox buyer Resolution Center (sandbox only,
with the live view shown in the video); (c) handle the case as a seller message plus a merchant refund through
the Refund API, with the dispute lifecycle shown through the merchant-side simulation endpoints. The product
story stays the same.
